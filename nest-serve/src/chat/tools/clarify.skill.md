# Clarify — 模糊意图澄清工具

## 职责

当用户输入模糊、过短、或明显是续问/追问时，**不查询知识库**，仅基于对话上下文分析用户可能想问的问题，以**自然语言反问文本**的形式直接返回给前端展示。像真人助手那样问用户："你是在问 A 吗？还是想了解 B？"

**核心原则：这是对话，不是选择题。**

## 触发条件（满足任一即触发）

1. 用户输入 ≤ 5 个字符
2. 输入包含典型模糊词：然后呢、咋整、所以呢、接下来、还有吗、再说点...
3. 纯语气词：啊、嗯、哦、哈

## ⚠️ 硬性约束：候选项必须从上下文实体派生

生成的候选项必须能从前序对话的「隐含实体」中派生，**不得凭空引入新实体**。

- 上文讨论 "Transformer" → 候选项只能是 "Transformer 的变体"、"Transformer 的训练"、"Transformer vs 其他架构"，**不能突然变成 "CNN"、"LSTM"**
- 上文讨论 "RAG 检索" → 候选项只能是 RAG 相关的延伸（重排序、召回率评估等），**不能跳到 "微调"、"提示工程"**

### 实体派生规则

1. **提取隐含实体池**：从前 2~3 轮对话中提取所有已出现的学术概念、方法名、模型名、数据集名
2. **候选项 = 实体 + 关系/属性/操作**：每个猜测必须是「已知实体 + 已知实体的某个方面」
3. **禁止跨域跳跃**：不能从讨论 A 突然跳到 B（除非 B 在上下文中被明确对比过）
4. **禁止泛化过度**：不能把具体方法泛化为完全不相关的大领域

## 输出格式

直接返回**自然语言反问文本**，作为助手的回复内容流式推送给前端：

```
你是在问 Transformer 自注意力机制的具体实现细节吗？
还是想了解它和普通注意力机制的区别？
或者你想知道如何在代码中实现自注意力？
```

内部同时携带结构化元数据（供日志/分析使用，不暴露给前端用户）：


## 生成规则

1. **自然语言优先**：输出必须是连贯的自然语言反问，像真人助手在确认需求
2. **必须结合上下文**：不能凭空生成，必须参考最近 2~3 轮对话主题
3. **🔒 实体封闭性**（硬性约束）：所有候选项的实体必须来自上下文实体池
4. **表述口语化**：不要像学术目录，要像人在说话
5. **去重**：与最近已问过的问题不能重复
6. **数量控制**：2~3 个猜测，用"是...还是...或者..."的句式串联
7. **置信度排序**：最可能的猜测放在最前面

## 正面示例

| 上下文 | 用户输入 | 生成结果（自然语言反问） |
|--------|---------|----------------------|
| 讨论 RAG 检索原理 | "然后呢" | "你是想了解 RAG 检索后的重排序怎么做？还是想知道召回率怎么评估？或者是混合检索里向量检索和关键词检索的权重怎么调？" |
| 讨论论文中的方法 | "咋整啊" | "你是想问这个方法的具体实现步骤？还是需要什么数据集？或者代码在哪里能找到？" |
| 首轮对话（无上下文） | "嗯" | "你好！你可以告诉我你想了解什么研究方向吗？比如检索某篇论文、解读一个文档、或者询问某个学术概念？" |

## 前端交互协议

Clarify 的输出就是一条普通的 `type: "answer"` 消息，**不需要特殊的事件类型**。前端正常渲染为助手回复文本即可。

## ⚠️ pendingConfirmation 防死循环机制

当 Clarify 被触发后，调用方应在会话状态中设置一个 `pendingConfirmation` 标记（TTL: 3 轮或 60s）。后续输入进入「确认解析模式」，不再重新触发 Clarify，避免"用户说'是'→再次澄清→无限循环"。

- 用户给出具体问题（长度>10 或含疑问词）→ 正常处理，退出 pending
- 用户说"是/对/好的"等确认词 → 映射到最高置信度候选项，退出 pending
- 用户说"不是/不对/另一个" → 映射到第二候选项，退出 pending
- 其他短输入 → 降级为 normal 处理，不再触发 clarify
- TTL 超时（60s 或满 3 轮）→ 自动退出到 normal

前端完全无感知，整个机制是服务端状态机。
