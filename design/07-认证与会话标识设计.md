# 07 · 认证与会话标识设计（token / userId / sessionId）

> 本文梳理后端的身份认证链路与数据标识体系：为什么选 token、token 如何签发、传递、校验，
> userId 如何成为数据隔离的分区键，sessionId 如何创建、回传、复用，以及两者为什么必须联合使用。
> 涉及 `py-serve/app/core`、`py-serve/app/userinfo`、`py-serve/app/chat` 与
> `project-user/src/api/request.ts`；前端 store 的细节见 [06](06-前端状态管理设计.md)。

---

## 一、两套标识的分工

系统里同时存在两个 id，它们是**两级键**，不是同一个东西：

| | **userId** | **sessionId** |
|---|---|---|
| 本质 | 用户主键（`userinfos._id`） | 一次会话的主键（`chatdata._id`） |
| 生成者 | 注册时 MongoDB `insert_one` 生成 | 首次对话时后端插入会话后生成 |
| 传输位置 | HTTP 头 `Authorization: Bearer <jwt>` | 请求体 `body.sessionId`（POST）/ query `?sessionId=`（GET/DELETE） |
| 信任级别 | **可信**：有签名，客户端伪造不了 | **不可信**：客户端可任意传值 |
| 作用 | 数据归属与隔离的分区键 | 定位"哪一整段对话" |
| 生命周期 | 长期（JWT 10 天） | 随会话创建与删除 |
| 记忆口诀 | 「数据归谁」 | 「说的哪一轮」 |

核心原则：**userId 只能从 token 里解出来，任何接口都不接受前端直接传 userId**；
sessionId 则是前端传来传去的，因此**必须与 userId 拼成联合条件**使用（见第六节）。

## 二、为什么是 token（方案选型的根因）

这一节记录"为什么这么做"的推理过程，避免以后只看到实现、不知道当初为什么否掉其他方案。

### 2.1 先分清两个被混在一起的问题

经常被当成一个问题的，其实是两件事：

| 问题 | 答案 | 性质 |
|---|---|---|
| 为什么 `registeruser` / `loginuser` 不挂 `Depends(get_current_user)`？ | 用户此刻还没有 token，要求鉴权就永远登不进来 | **bootstrap（鸡生蛋）问题**：任何鉴权方案都必须豁免登录类接口，包括 session 方案 |
| 为什么用 token，而不是 cookie + session？ | HTTP 无状态 + 本项目的部署与跨域约束 | **方案选型问题**：这才是本文要论证的 |

也就是说，"第一次登录没有 token"只能解释"为什么那两个接口豁免鉴权"，
**不能**解释"为什么选 token"。

### 2.2 两条技术路线的本质差异

| 维度 | Session + Cookie | Token（当前方案） |
|---|---|---|
| 凭证存放 | 浏览器 cookie（自动存取、自动携带） | 请求头 `Authorization`（客户端显式携带） |
| 服务端是否存登录记录 | 存：redis 里 `{sessionId: userId}` | 不存：签名自证 |
| 每次请求的额外开销 | 一次存储查询 | 一次验签（纯本地计算） |
| 跨域要求 | `withCredentials` + 具体 origin（不能用 `*`）+ `SameSite=None` + 必须 HTTPS | `allow_headers` 放行一个普通请求头即可 |
| 非浏览器端 | 需要自行实现 cookie 存储与匹配 | 任何能发 HTTP 的客户端都能用 |
| 主动失效 | 删 session 即可 | 做不到（除非额外引入黑名单） |

### 2.3 支持 token 的三个理由，以及各自的强弱

**① 跨域（当前成立，但可被消解）**

前端 Vite 跑在 `localhost:5173`，后端跑在 `127.0.0.1:3000`，`vite.config.ts` 里没有配
`server.proxy`，所以是真正的跨域，靠 `main.py` 的 `CORSMiddleware(allow_origins=["*"])` 放行。

`Authorization` 只是一个服务端声明放行的普通请求头；而 cookie 跨域是另一套规则：必须
`withCredentials` + 服务端 `Access-Control-Allow-Credentials`（此时 origin 不能是 `*`）+
`SameSite=None`（又强制 `Secure`，本地 http 开发直接卡死）。

> 这条理由有前提：如果以后给 Vite 配上 `server.proxy` 把 `/chat`、`/file_management`
> 代理到 3000，前后端就变成同源，这条理由自动消失。

**② 无状态（最硬的理由）**

服务端不为"谁登录了"保存任何记录，`deps.py` 里 `jwt.decode(...)` 一步完成身份确认，
鉴权链路零存储查询。带来的实际收益：

- 后端重启不掉登录态；
- 多实例负载均衡不需要 sticky session，也不需要共享会话库；
- 每个请求少一次 redis 往返。

这条与部署形态无关，是三个理由里最经得起推敲的。

**③ 多端复用（目前是潜力，不是刚需）**

token 是普通 HTTP 头，所以除浏览器外，命令行、App、其他后端都能直接复用同一套接口：

```bash
# 1. 拿 token（此接口无需前置认证 —— bootstrap）
curl -X POST http://127.0.0.1:3000/userinfo/loginuser \
  -H "Content-Type: application/json" \
  -d '{"phoneNumber":"13800138000","password":"Abc12345"}'

# 2. 带 token 调受保护接口，全程不涉及 cookie
curl http://127.0.0.1:3000/chat/sessionlist \
  -H "Authorization: Bearer <上一步返回的 token>"
```

cookie 是浏览器专属机制（自动按域名匹配、自动携带），脚本与 App 里没有这套东西。
不过需要诚实说明：当前只有 Vue 一个客户端，这条属于"为未来留余地"，不是当下的痛点。

### 2.4 代价：无状态的三个账单

| 代价 | 现状 | 真要解决时的做法 |
|---|---|---|
| 无法即时吊销 | 登出只是前端清 store，服务端无感知；旧 token 在 10 天内仍可通过验签 | 引入黑名单（redis 存 `jti`）或 `tokenVersion` 字段 |
| 权限策略变更不生效于旧 token | payload 里只有 `user_id`，没有角色字段 | 加角色后需等旧 token 过期，或用短有效期 + refresh |
| payload 明文可见 | JWT 是 base64 编码而非加密，任何人都能解开 | 因此 payload 只放 `user_id`，不放手机号/密码散列等 |

### 2.5 还有第三条路：不透明 token（redis 查表）

"用 token"不等于"必须用 JWT"。另一种常见做法是**随机串 + 服务端查表**：

```
登录 → 生成 uuid 当 token → redis 存 {token: userId}，TTL 滑动续期
请求 → 带 token → 服务端查 redis 拿到 userId
```

| | 自包含 JWT（当前） | 不透明 token + redis |
|---|---|---|
| 每次请求开销 | 验签（纯计算） | 一次 redis 查询 |
| 主动吊销 | 做不到 | 删 key 即可 |
| 权限/资料变更 | 需等 token 过期 | 改 redis 即时生效 |
| 部署依赖 | 无 | 依赖 redis 可用 |

**取舍本质**：现在这套是拿"吊销能力"换了"零存储查询"。等出现"退出登录立即失效"、
"踢下线"、"管理员/普通用户分权"这类需求时，就该换成不透明 token 或加黑名单——
届时改动集中在 `core/deps.py` 与 `userinfo/service.py`，业务代码无需动。

### 2.6 什么情况下反而该用 session

不是"token 更先进"。如果满足以下全部条件，session + cookie 更省事：
纯同域部署、只服务浏览器、且需要强会话控制（例如后台管理系统随时踢人、单点登录、
会话列表管理）。

## 三、token 链路

### 3.1 签发（`app/userinfo/service.py`）

注册与登录共用同一套签发逻辑：

```python
# userinfo/service.py · create_token
payload = {
    "token": str(user_id),          # 关键：payload 里只放用户 _id
    "iat": datetime.now(timezone.utc),
    "exp": datetime.now(timezone.utc) + timedelta(days=Config.JWT_EXPIRE_DAYS),
}
return jwt.encode(payload, Config.JWT_SECRET, algorithm="HS256")
```

三个设计点：

1. **payload 只放 user_id**，不放手机号、密码散列等敏感字段——JWT 是 base64 编码而非加密，
   任何人都能解开看到内容（理由与代价见 2.4）。
2. **密码不直接落库**，`hash_password()` 用 `PASSWORD_KEY` 做 HMAC-SHA256（`userinfo/service.py`），
   登录时比对散列值。
3. **无状态**：服务端不存 session/token 表，登出由前端清空本地 token 完成——选型理由见第二节，
   代价见 2.4。

### 3.2 传输（`project-user/src/api/request.ts`）

两条路径都要带 token，注意它们是**两处独立实现**：

| 场景 | 注入方式 | 位置 |
|---|---|---|
| 普通 REST（axios） | 请求拦截器统一注入 | `request.ts` 拦截器 |
| 流式对话（SSE） | `fetchEventSource` 手动写 headers | `request.ts · SendMessageApi` |

SSE 之所以要手写，是因为浏览器原生 `EventSource` 不支持自定义请求头，这也是当初选
`@microsoft/fetch-event-source` 的原因之一（详见 [05](05-流式协议SSE改造.md)）。

token 失效时统一兜底：axios 响应拦截器识别 401 → 置 `showLoginPopup = true` 弹出登录框。

### 3.3 校验（`app/core/deps.py`）

```python
# core/deps.py · get_current_user
token = _extract_token(request)              # 严格解析 "Bearer <jwt>" 两段式
payload = jwt.decode(token, Config.JWT_SECRET, algorithms=["HS256"])
if not payload.get("token"):
    raise _unauthorized("token is invalid")  # 防止空 payload 被当作有效身份
return AuthUser(payload)
```

`AuthUser` 是 `dict` 的子类，只额外提供 `.user_id` 属性，直接返回 `payload["token"]`。

使用方式（每个受保护接口一行）：

```python
user: AuthUser = Depends(get_current_user)
user_id = user.user_id
```

已挂载该依赖的接口：

| 模块 | 接口 |
|---|---|
| chat | `POST /chat/sendmessage`、`GET /chat/sessionlist`、`GET /chat/history`、`DELETE /chat/deletesession` |
| file_management | 全部 9 个接口 |
| userinfo | 仅 `GET /userinfo/me`（自检用）；注册/登录本身不需要 token（bootstrap，见 2.1） |

### 3.4 为什么 `AuthUser` / `get_current_user` 放在 `core` 而不是 `userinfo`

全仓检查过：**除 `main.py` 注册路由外，没有任何业务代码 import `userinfo`**。认证能力属于
横切基础设施，若放在 userinfo 内，会形成业务包之间的横向依赖：

```
chat/router.py            ──▶ userinfo/...     ← 业务包依赖业务包
file_management/router.py ──▶ userinfo/...
```

收敛到 `core/deps.py` 后，依赖方向变为单向：

```
userinfo ─┐
chat ─────┼──▶ core/deps.py（验签）、core/config.py（密钥）
file_mgmt ┘
```

三个业务包互不依赖，只依赖 core。这也是 `config.py` / `response.py` 一并迁入 `core/` 的理由。

## 四、userId 作为数据隔离键

`user_id` 从 token 解出后，成为所有存储的**分区键**：

| 存储 | 隔离方式 | 位置 |
|---|---|---|
| MongoDB · 文件 | `fileanagements.userId = user_id` | `file_management/service.py`（写入 / 查询 / 删除均带该条件） |
| MongoDB · 会话 | `chatdata.userId = ObjectId(user_id)` | `chat/session.py`（创建 / 读取 / 删除） |
| Milvus | **每用户一个集合**，集合名 `_{user_id}` | `file_management/milvus_store.py · collection_name_for` |
| Redis | key 前缀 `chat_history:{user_id}:{session_id}` | `chat/session.py · _redis_key` |

除"查询时带上条件"外，删除与读取路径还有显式的**归属校验**：

```python
# file_management/service.py · delete_file / assert_file_ownership
if doc.get("userId") != user_id:
    raise BizError(...)
```

即：A 用户拿到 B 用户的 `fileId` 也删不掉、读不到。

## 五、sessionId 生命周期

### 5.1 状态流转

```
无会话                     会话中                      已删除
sessionId=null  ──首轮消息──▶  sessionId="66f2a3..."  ──删除会话──▶  回退到 null
       │                          │  ▲
       │                          │  └── 每轮请求回传
       └────── 后端创建后经 SSE 首帧回传 ──┘
```

### 5.2 创建与回传

1. 前端首轮发送时 `sessionId` 为字符串 `"null"`（约定占位符，见 5.3）；
2. 后端 `chat/service.py · combine_convo` 判断 `is_new_session = session_id == "null"`；
3. 新会话走 `chat/session.py · create_session()`：插入 `chatdata`，`chatList` 直接带上本轮用户消息；
4. 拿到 `inserted_id` 后，作为 SSE **首帧**推给前端：

```
data: {"type":"sessionId","sessionId":"66f2a3..."}
```

先发 id 再流式输出正文，是为了保证即使后续生成失败，前端也已持有可继续对话的会话 id。

### 5.3 前端存储

- 内部状态用 `null` 表示"还没有会话"，发请求时才由 getter `sessionIdForApi` 序列化为 `"null"`；
- `setSessionId()` 同时写 Pinia 与 `localStorage`（key = `sessionId`），刷新页面后仍能续上；
- 细节见 [06 · 关键设计决策 1](06-前端状态管理设计.md)。

### 5.4 复用与查询

| 操作 | 调用 | 参数位置 |
|---|---|---|
| 继续对话 | `POST /chat/sendmessage` | 请求体 `sessionId` |
| 查看历史 | `GET /chat/history` | query `?sessionId=` |
| 删除会话 | `DELETE /chat/deletesession` | query `?sessionId=` |

GET/DELETE 用 query 而非路径参数，是因为它们没有请求体；`sessionId` 作为查询条件而非资源路径，
语义上也更贴近"筛选某个会话的记录"。

### 5.5 缓存策略

- 历史消息读多写少，故 MongoDB 为准、Redis 做热缓存，TTL 3 小时（`HISTORY_TTL = 10800`）；
- 读：`load_history()` 先查 Redis，未命中回源 Mongo 并回填；
- 写：`persist_convo()` 追加到 Mongo `chatList` 后刷新 Redis；
- 删：`delete_session()` 删 Mongo 文档同时删 Redis key，避免删完还能读到缓存。

## 六、为什么必须联合查询（安全边界）

假设某处写成只按 sessionId 查：

```python
# 反例：只按 _id 查
chat_data = await chat_col.find_one({"_id": session_oid})
```

那么任何人只要能拿到别人的 sessionId（会话列表接口、浏览器历史、截图都可能泄露），
就能通过 `GET /chat/history?sessionId=<他人的>` 读到他人全部对话，
`DELETE /chat/deletesession?sessionId=<他人的>` 直接删掉他人会话。

现状全部采用**双条件**，实际代码：

```python
# chat/session.py · load_history / persist_convo
{"userId": ObjectId(user_id), "_id": session_oid}
```

附带一个行为细节：传别人的 sessionId 时，查询命中不到 → 返回**空 `chatList`**，而不是报 403。
这样不泄露"该会话是否存在"，属于有意为之的静默降级。同理，`ObjectId(...)` 解析失败
（比如乱传一个非 24 位十六进制串）也返回空列表而不抛错。

## 八、已知限制与后续可选

| 项 | 现状 | 影响 / 可选改法 |
|---|---|---|
| token 无刷新机制 | 有效期固定 10 天（`JWT_EXPIRE_DAYS`），过期后 401 弹登录框 | 需要长会话体验时，可加 refresh token 或滑动续期 |
| 密钥有默认值 | `config.py` 中 `JWT_SECRET` / `PASSWORD_KEY` 带硬编码兜底 | 生产环境必须用环境变量覆盖，否则可被伪造 token |
| 登出仅前端 | JWT 无状态，前端清 store 即视为登出 | 若需强制失效，得引入黑名单（Redis 存 jti）或改用不透明 token（见 2.5） |
| 无角色 / 权限模型 | 只有"认证 + 数据归属隔离"，没有 RBAC | 加角色后需考虑旧 token 不含角色字段的问题（见 2.4） |
| sessionId 存 localStorage | 多标签页共享同一 key，切换会话会互相影响 | 需按标签页隔离时改用 `sessionStorage` |
| 会话列表无分页 | `get_session_list` 一次返回全部会话（按 `createTime` 倒序）；查询时虽把整条 `chatList` 取回内存（用于生成标题与条数），但响应体只返回摘要字段 | 会话数增长后会变慢，可加 `limit` + 游标分页，并把标题在写入时冗余存一份以避免回读 `chatList` |

## 九、验证方式

- `python -c "from app.main import app"` 可正常导入，路径级回归以路由清单比对为准；
- 手工链路验证（需 Mongo / Redis 在线）：
  1. 注册 → 拿 token；
  2. 不带 token 请求 `GET /chat/sessionlist` → 401；
  3. 带 token 发首轮消息 `sessionId="null"` → SSE 首帧返回新 sessionId；
  4. 用他人 token 请求 `GET /chat/history?sessionId=<自己的>` → 返回空 `chatList`（不越权）；
  5. 删除会话后立即读取 → Redis key 已清，返回空。
