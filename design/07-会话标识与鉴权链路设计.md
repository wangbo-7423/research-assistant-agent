# 07 · 会话标识与鉴权链路设计（token × sessionId）

> 本文把两条身份线放在一起讲：**token 解决"你是谁"**，**sessionId 解决"哪段对话"**。
> 覆盖从登录签发、首轮建会话、SSE 回传会话 id、到后续续接历史的完整链路，
> 以及"`null` → `"null"` → 真实 id"这个状态迁移背后的契约与风险。
> 涉及 `project-user/src`（api / store / 组件）与 `py-serve/app`（core / chat）。
> 前端状态层的拆分与持久化细节见 `06-前端状态管理设计.md`，本文不重复。

---

## 一、为什么需要两个标识

| | `token` | `sessionId` |
|---|---|---|
| 回答的问题 | 你是谁（哪个用户） | 哪一段对话 |
| 签发者 | `userinfo/service.create_token()` | `chat/session.create_session()` 返回的 Mongo `_id` |
| 形态 | JWT，三段式 | ObjectId 字符串（24 位十六进制） |
| 有效期 | 10 天（`JWT_EXPIRE_DAYS`） | 永久，除非显式删除 |
| 传输位置 | 请求头 `Authorization: Bearer` | 请求体（POST）或 query（GET / DELETE） |
| 后端如何使用 | 验签后取出 `userId` | 仅作为查询条件 |
| 一个用户有几个 | 1 | N |

关系：**`sessionId` 是挂在 `userId` 下的资源编号**。

```
用户 A (userId=671a…0001)
 ├── 会话 671a…1001
 ├── 会话 671a…1002
 └── 会话 671a…1003

用户 B (userId=671a…0002)
 └── 会话 671a…2001
```

所以 `sessionId` 单独没有意义，必须与 token 配对使用。

## 二、握手流程（五步）

### ① 前端初始态：`sessionId = null`

```17:24:project-user/src/store/chat.ts
  state: () => ({
    sessionId: null as string | null,
    messageList: [] as MessageListType[],
  }),
  getters: {
    // 请求体里用的 sessionId，屏蔽后端 "null" 字符串的约定
    sessionIdForApi: (state): string => state.sessionId ?? NEW_SESSION_ID,
  },
```

**内部用 `null`，出口转 `"null"`**，原因是两者语义不同：

| 值 | 含义 | 关键点 |
|---|---|---|
| `null`（JS） | "还没有会话" | `if (chat.sessionId)` 能正确判为假 |
| `"null"`（字符串） | 协议占位符，请求后端开新会话 | 后端 `session_id == "null"` 判断用 |

若内部也用字符串 `'null'`，它是 **truthy**，所有"是否新会话"的判断都会失效——这是本次重构修正的核心缺陷。

**为什么不能用 JSON `null` 传？** 后端 `SendMessageDto.sessionId: str`，传 `null` 会被 Pydantic 拦成 422。所以 `"null"` 是**不可替换的协议常量**。

建号时同时把首条用户消息落库：

```20:31:py-serve/app/chat/session.py
async def create_session(user_id: str, first_message: dict, chat_col) -> ObjectId:
    """新建会话：首条用户消息随会话一起落库。"""
    now = datetime.now()
    created = await chat_col.insert_one(
        {
            "userId": ObjectId(user_id),
            "createDate": now.strftime("%Y-%m-%d"),
            "createTime": int(now.timestamp() * 1000),
            "chatList": [first_message],
        }
    )
    return created.inserted_id
```

两个要点：

- `_id` 由 Mongo 生成，前端无法伪造；
- `userId` 来自 token，不来自请求体；
- 首条用户消息已随会话写入，因此后续 `persist_convo` 的 `is_new_session` 分支只需追加助手回复，避免重复插入。

## 四、安全边界：sessionId 不是凭证

后端所有会话操作都同时按 `userId` 与 `_id` 过滤：

| 操作 | 过滤条件 | 位置 |
|---|---|---|
| 读历史 | `{"userId", "_id"}` | `session.py:44` |
| 追加消息 | `{"_id", "userId"}` | `session.py:68` |
| 删除会话 | `{"userId", "_id"}` | `session.py:111` |
| 列会话 | `{"userId"}` | `session.py:82` |
| Redis 缓存 key | `chat_history:{userId}:{sessionId}` | `session.py:16-17` |

结论：

- 即使拿到他人 `sessionId`，请求也会因 `userId` 不匹配而得到空结果；
- **越权防护靠"配对"而非"保密"**——id 是否可猜并不重要，重要的是它必须与 token 解出的 `userId` 同时命中；
- 因此 `sessionId` 可以放在 URL query 里（如 `GET /chat/history?sessionId=…`），不构成敏感信息泄露；而 token 必须放 header，不能进 URL（会落访问日志与浏览器历史）。

## 五、前端状态机

| 场景 | sessionId 来源 | 触发 action |
|---|---|---|
| 页面打开 / 新建对话 | `null` | `resetSession()` |
| 新会话首轮 | SSE `type: "sessionId"` 帧 | `setSessionId()` |
| 点击左侧历史会话 | 列表项 `item.sessionId` | `loadSession()` |
| 删除正在查看的会话 | 归零 | `resetSession()` |

```
        ┌──────────── resetSession() ────────────┐
        ▼                                        │
   sessionId = null  ──首轮 SSE 帧──▶  真实 id ──┤
        │                                 ▲     │
        └────── loadSession(历史 id) ──────┘     │
                                    deleteSession(当前会话)
```

`loadSession` 同时替换 `sessionId` 与 `messageList`——**切换会话 = 换钥匙 + 换一屏内容**。

## 六、为什么必须由前端回填

HTTP 是无记忆的：请求 2 到达时，后端完全不记得请求 1 给谁开过号。若后端为此维护一张"谁刚开过号"的表，那便退化成了 session 方案。

因此**会话归属只能由客户端在下次请求时交回**。这也是"无状态"的代价与前提：

```
POST /sendmessage (sessionId="null")  → 后端开号、返回
POST /sendmessage (sessionId=真实id)  → 后端凭 id 捞历史
```

## 七、边界与风险

| 情况 | 现状 | 影响 |
|---|---|---|
| 文件校验失败（`service.py:54-56`） | 在 `create_session` 之前 return | 不产生空会话记录 ✅ |
| SSE 在 sessionId 帧后、回答前断开 | 会话已在 Mongo 创建，前端可能未收到 id | 列表出现"孤儿会话" |
| 前端未收到 sessionId 帧 | 下一条仍发 `"null"` | 重复建号，产生两条记录 |
| 刷新页面 | `sessionId` 写入 localStorage 但无回读 | 回到 `null`，变成新会话 |
| 快速连点发送 | `sending` 标志挡住；后端无幂等键 | 一旦绕过前端限制即产生重复会话 |
| 流开始后出错 | HTTP 状态码已发出（200） | 错误只能以 `{"type":"error"}` 帧表达，无法改状态码 |

第 2、3、5 条的共同根因是**缺少幂等键**：请求没有可供后端去重的标识。

## 八、后续可选增强

| 增强 | 做法 | 解决的风险 |
|---|---|---|
| 请求幂等 | 前端生成 `clientRequestId` 随请求发送，后端按 `(userId, clientRequestId)` 去重 | 重复建号、孤儿会话 |
| 会话回读 | 新增 `initSessionFromStorage()`，与 `messageList` 持久化一起做 | 刷新后会话丢失 |
| 失败补偿 | 前端超时未收到 `sessionId` 帧时，提示"重试"而非静默续发 `"null"` | 重复会话 |
| 上下文窗口 | 当前固定取最近 21 条，可改为按 token 预算动态截断 | 长对话成本与丢上下文 |
| 会话软删除 | `delete_one` 改为标记删除 | 误删不可恢复 |

## 九、验证要点

| 用例 | 预期 |
|---|---|
| 首轮发送 | 请求体 `sessionId` 为字符串 `"null"`；响应含且仅含一帧 `type:"sessionId"` |
| 次轮发送 | 请求体为真实 id；后端不再推送 `sessionId` 帧 |
| 越权读取 | 用 A 的 token 请求 B 的 `sessionId`，`history` 返回空 `chatList`，不报 403 |
| 删除他人会话 | `deleted: false` |
| 新建对话 | `sessionId` 复位 `null`，`messageList` 为空，列表新增一条记录 |
| 刷新页面 | 登录态保留（token 恢复），会话回到空白新会话（当前设计，见第七节） |
