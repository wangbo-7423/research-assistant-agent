# 01 · 经典多路召回（通道侧）

> 定义：对**同一个查询**，并行使用多个检索通道（向量语义 / 关键词 / 元数据 / …），
> 再用融合算法（本项目用 RRF）合并排序。治的病是「单一通道的表征偏差」。

---

## 一、本项目实现

`nest-serve/src/fileanagement/fileanagement.service.ts` 的 `hybridSearch`：

```
query ──┬─► vectorSearch（text-embedding-v3 → Milvus COSINE，候选 limit×2）
        │
        └─► keywordSearch（DeepSeek 抽取关键词 → Milvus docText LIKE 匹配）
                  │
                  ▼
        RRF 融合：score = Σ weight / (60 + rank)
        默认权重：向量 0.7 / 关键词 0.3
```

特点：两路并行、关键词路失败降级为纯向量（不阻断）、结果按 RRF 分数排序截断。

---

## 二、实测价值（2026-09-07，865-chunk 实验库，8 个评价类问题）

| 路径 | 方面覆盖 |
|---|---|
| 单向量 top12（A12v） | 0.269 |
| 向量+关键词 RRF top12（A12，经典多路） | 0.269 |

**通道融合增量 = 0。** 与 2026-08-11 的扫参结论一致（"RRF 权重 0.5~0.9 结果基本一致，
当前库中向量/关键词高度重合"）。

原因分析：

1. **语料同质**：学术论文 + 面经都是规范书面语，语义检索和关键词检索命中同一批 chunk；
2. **查询类型**：评价类问题的关键词（"评价""怎么看"）没有区分度，关键词路退化为向量路的子集；
3. **两路取的是同一候选池的头部**：融合只是重排，召回集合本身没变。

> ⚠️ 注意：这个结论**受限于当前语料**。如果未来加入代码、表格、编号密集的文档
> （关键词路对精确符号有优势），或用户查询包含大量专有名词/编号，通道融合的价值会回来。
> 扩库后应重跑 `eval/runners/scan-retrieval-params.ts` 验证。

## 三、设计建议

| 决策 | 结论 |
|---|---|
| 是否保留 | **保留**，作为永远开启的默认层——成本可忽略（两路并行，延迟取最大者），且是防御性的 |
| 是否值得调参 | 不值得。RRF 权重、候选宽度在当前语料上无区分度 |
| 是否指望它解决覆盖问题 | **不能**。它治的是表征偏差，不是语义覆盖——后者是查询侧（02）和时间侧（03）的问题 |
| 监控点 | `fromVector` / `fromKeyword` 数量比（trace 里已有）：如果关键词路持续贡献 ≈0 的独特结果，可以考虑下线简化 |

---

## 四、一句话总结

经典多路召回是**便宜的地基**，不是**增量的引擎**。它保证"通道不出错"，
但回答"怎么召回得更全"要靠 02（查询侧）和 03（时间侧）。
