# 08 · 文档解析与切片链路

> 本文记录 py-serve 从「上传文件」到「可检索 chunk」的完整 as-built 逻辑，
> 包括 PDF/DOCX 解析、论文结构识别、递归切片、父子文档与元数据落库。
> 对应代码：
> `app/file_management/parsers.py`、`structure.py`、`splitter.py`、
> `sections.py`、`service.py`、`milvus_store.py`。
>
> 图像/图表的抽取不在本链路内，见 [09-图像与图表提取设计](09-图像与图表提取设计.md)。
> 入库后基于 chunk 生成 QA 问题索引的检索方案，见 [10-QA问题索引双路召回](10-QA问题索引双路召回.md)。

---

## 一、总览

```
上传 PDF/DOCX（≤5MB）
   │
   ▼
parse_file_with_pages
   ├─ PDF  : pypdf 逐页抽文本，同时记录每页起始字符偏移 pageStarts
   └─ DOCX : python-docx 按 body 顺序抽段落 + 表格（表格转 markdown），pageStarts=[]
   │
   ▼
MongoDB `fileanagements`
   ├─ fileText    : 解析后的全文（唯一事实来源）
   └─ pageStarts  : PDF 每页起始偏移（重建索引时还原页码）
   │
   ▼
split_document_with_sections
   ├─ detect_sections      : 识别章节标题，产出区间 + 层级路径
   ├─ _group_by_chapter    : 只在「一级章节」之间断开
   ├─ recursive_character_split : 章节内递归切成 800/100 的 chunk
   └─ 回填 section/page/para/charStart/charEnd/parentId
   │
   ├──► Milvus `_<userId>_v3`   : 子块文本 + 向量 + 溯源标量
   └──► Mongo  `file_sections`  : 父文档（一级章节全文 + 页码区间 + 路径）
```

两个关键设计：

| 决策 | 理由 |
|---|---|
| 只存解析后的文本，不存原始 Buffer | 上传接口原本只处理文本；但这也导致「页码无法回填」「图表无法截图」两个后遗症（见第七节） |
| 子块进 Milvus、父章节进 Mongo | Milvus `VARCHAR` 上限 9000，父章节动辄上万字；父章节也不参与向量检索，只需要按 `parentId` 回表 |

## 二、解析层

### 2.1 PDF

`parse_pdf_with_pages` 的实现是逐页 `extract_text()`，并把每页文本拼成：

```
page_0_text + "\n" + page_1_text + "\n" + ...
```

同时记录 `page_starts[i]` = 第 i 页文本在全文中的起始字符偏移。该偏移是后续
「chunk → 页码」的唯一依据，因此**任何会增删字符的后处理都必须同步调整偏移**，
否则页码会整体错位。

当前范围：

- 仅做纯文本抽取，**不做版面分析、不区分正文/表格/图片/公式**；
- 扫描件（无文本层）会得到空文本，当前没有 OCR 兜底；
- 公式会被抽成线性字符（如 `softmax(QK^T/√d_k)V`），结构信息丢失；
- 双栏论文依赖 pypdf 的阅读顺序，跨栏段落可能交错。

**为什么 PDF 表格不转 markdown？**
曾用 pdfplumber 对整页表格做结构化，实测在双栏论文上会按 `top → x` 排序，
把左右两栏文字逐行交错拼接，chunk 级召回从 66.9% 掉到 48.5%（10 篇论文无一篇幸免）。
该方案已废弃，原因与数据记录在 `parsers.py:9-13`。结论：**表格结构化必须按区域做，
不能整页做**，这直接影响了 09 的设计。

### 2.2 DOCX

`parse_docx` 不直接遍历 `document.paragraphs`（那样会 100% 丢失表格），而是按
`document.element.body` 的原始顺序遍历：

- `w:p` → 段落文本；
- `w:tbl` → 二维单元格转 markdown 表格，保持它在正文中的位置；
- 块之间用空行连接。

因此 DOCX 的段落边界最可靠，但**内嵌图片不会进入文本**，图片同样需要 09 的抽取链路。

### 2.3 边界与校验

| 项 | 当前值 |
|---|---|
| 允许类型 | `application/pdf`、DOCX（OpenXML） |
| 单文件大小 | 5MB |
| 单次上传 | 最多 3 个 |
| 知识库/对话框 | `uploadType=UD` 才建索引；`UB` 只存文本供临时问答 |

## 三、结构识别

`detect_sections(text)` 按行扫描，识别「标题行」，产出 `Section(title, level, start, end, path)`。

### 3.1 什么算标题

四类规则，全部通过才算：

1. **编号标题**：`1`、`2.1`、`3.2.1`（最多四段），标题部分通过大小写启发式；
2. **罗马数字标题**：`III. METHOD`、`IV. Results`；
3. **中文序号标题**：`一、引言`、`1、方法`；
4. **无编号常见章节名**：`Abstract`、`Introduction`、`Method`、`Experiments`、
   `Conclusion`、`References`、`摘要`、`引言`、`参考文献` 等白名单。

同时排除：

- 行长度 > 90 或标题部分 > 60；
- 行尾是 `。，；：、,;:`；
- 目录行（连续点线、行尾页码）；
- 列表/表格行（以 `-•·*` 开头或含 `|`）；
- 「编号列表伪装成标题」：`1. We propose ...` 这类句子开头的英文小写实词。

### 3.2 层级与路径

层级由编号点数决定（`3` → 1，`3.2` → 2），无编号白名单标题统一为一级。
用栈维护祖先链，得到 `path = ("3 Method", "3.2 Encoder")`。

特殊处理：

- 首个标题之前的正文记为根章节 `正文`；
- 遇到 `References / Bibliography / 参考文献` 后**停止识别**，否则参考文献条目会被
  当成大量伪章节；
- 标题重复（PDF 页眉反复出现 `3 Method`）在分组阶段合并，不重复开章。

### 3.3 可信度兜底

```python
_MAX_SECTIONS = 80        # 章节数超过 80 → 基本是误判
_MIN_SECTION_CHARS = 150  # 平均章节长度 < 150 → 误判
```

不满足可信度时，整篇退化为一个 `正文` 章节。这条兜底保证了「识别失败不会比改造前更差」，
但也会让结构信息的收益在个别 PDF 上归零（例如 Illustrated Transformer 只识别出 2 个章节）。

## 四、切片

### 4.1 递归字符切片

`recursive_character_split` 对齐 LangChain `RecursiveCharacterTextSplitter`：

| 参数 | 值 |
|---|---|
| `chunk_size` | 800 字符 |
| `chunk_overlap` | 100 字符 |
| 分隔符优先级 | `\n\n` → `\n` → 空格 → 空串 |

行为要点：

- 先按最高优先级切分，单段仍超长时才递归到下一级；
- 合并时保留 `chunk_overlap` 的回退窗口；
- 对结果做 `strip()`，空块丢弃。

### 4.2 章节内切块，而不是整篇切块

`split_document_with_sections` 先按**一级章节**分组，再在组内递归切分：

- 好处：chunk 不会横跨「方法」和「实验」两章，`section` 标签更可信；
- 章节内部的二三级标题不单独断开，避免产生大量几十字的碎片；
- 同一标题重复出现（页眉）时并入上一组。

### 4.3 附加清理

- **标题独占块过滤**：当标题后面紧跟一个超过 800 字的长段落时，递归切分会把标题行
  单独切出来（如 8 字的 `Abstract`）。这类块没有有效内容，直接丢弃；
- **空块过滤**：`strip()` 后为空的不入库；
- 切分后按原文顺序回填 `chunk_index`，`chunkKey = f"{docId}#{chunkIndex}"`。

### 4.4 元数据

每个 `ChunkSpan` 最终写入 Milvus 的字段：

| 字段 | 含义 | 生成方式 |
|---|---|---|
| `chunkKey` | 文档内唯一键 | `docId#chunkIndex` |
| `parentId` | 所属父章节（一级章节） | `docId#s{chapterIndex}` |
| `chunkIndex` | 切片序号 | 按输出顺序 |
| `section` | 章节路径 | `" > ".join(path)` |
| `page` | 起始页码（1 起，0=未知） | `bisect(page_starts, charStart)` |
| `para` | 章节内段序（0=不可靠） | 空行切段后定位；单段且 > 1200 字视为不可靠 |
| `charStart` / `charEnd` | 全文绝对字符区间 | `text.find(chunk, cursor)` |

`charStart/charEnd` 是最精确的程序级锚点，`page/section/para` 是给人看的定位信息。
两者的对应关系完全依赖解析阶段记录的 `pageStarts`。

## 五、父文档

`split_document_with_sections` 同时产出 `DocSection`：

```text
parentId   docId#s2
path       3 Method
level      1
start/end  一级章节的全文字符区间
pageStart/pageEnd
text       一级章节全文（含其下所有小节）
```

父文档按**一级章节**落库，而不是按每个二三级小节：

- 小节可能只有几十个字（例如 `Results` 后面紧跟 `Results > Additional Results`），
  拿它当父文档会让上下文窗口被压到十几个字符；
- 子块的 `section` 仍记录它起点所在的小节路径，`parentId` 指向所属一级章节，
  这样「标签精细」和「上下文完整」各司其职。

- 写入 Mongo `file_sections`（`userId` + `docId` + `parentId` 建索引）；
- 子块只存 `parentId`，不复制父文本；
- 父章节只在生成阶段按 `parentId` 批量回表，不参与向量检索；
- 检索侧按父章节聚合去重后，截取「子块 ± 600 字、单片段 ≤ 2400 字」的窗口注入模型
  （见 `app/chat/retrieval.py`）。

删除文件时的顺序：先删 Milvus 向量 → 再删 `file_sections` → 最后删 `fileanagements`，
避免留下孤儿向量。

## 六、入库与版本

### 6.1 MongoDB

`fileanagements`：

```text
userId, fileName, fileType, fileSize, fileText, pageStarts,
uploadType(UD|UB), createdAt, updatedAt
```

`file_sections`：

```text
userId, docId, docTitle, parentId, path, level,
start, end, pageStart, pageEnd, text
```

### 6.2 Milvus

集合名：`_<userId>_v3`（每用户一个，天然隔离）。

```text
id Int64 主键（手动生成）
docId / docTitle / docText
parentId / chunkKey / chunkIndex
section / page / para / charStart / charEnd
docVector FloatVector(1024)
```

索引：`IVF_FLAT` + `COSINE`，`nlist=128`，检索 `nprobe=10`。

### 6.3 向量化

- 模型：通义 `text-embedding-v3`，1024 维；
- 批量：10 条/批（通义接口限制）；
- 查询向量带 500 条 FIFO 缓存（评测时同一 query 会被反复使用）；
- 空文本用单个空格占位，接口返回数量不足时降级为逐条生成。

### 6.4 版本与重建

Milvus 不支持给已有集合加列，因此每次 schema 变更都用新集合名（v2 → v3），旧集合保留。
存量文件通过：

```bash
python scripts/reindex_kb.py --prune-legacy
```

从 Mongo `fileText` / `pageStarts` 重建向量与父章节，并在成功后清理旧版本集合。

## 七、已知边界

| 边界 | 表现 | 影响 | 对策 |
|---|---|---|---|
| 图片完全缺失 | 图注在文本里，图本身不在索引 | 图相关问题的覆盖率是 0 | 见 09：图片裁剪 + 视觉描述 |
| PDF 表格不结构化 | 数值以纯文本散落在 chunk 中 | 能答但易错、不可核对 | 见 09：按区域转 markdown |
| 公式线性化 | 上下标/分式结构丢失 | 公式类问题答不准 | 09 的 formula 元素（低优先级） |
| 扫描件无文本层 | `fileText` 接近空 | 文件“上传成功但搜不到” | 增加 OCR 兜底（未实现） |
| 个别 PDF 乱码 | 如 DeepSeek-R1 的表格区域出现 NUL/乱序 | 检索与引用同时受污染 | 换 PyMuPDF 做解析基线对比 |
| 标题漏判 | Illustrated Transformer 只识别 2 章 | 章节标签退化为大区间 | 补充常见标题模式；失败时依赖 `正文` |
| 段序不可靠 | PDF 无段间空行，`para=0` | 引用只能显示到章节/片段 | 保持 0，不伪造段序 |
| 存量文件无页码 | 改造前上传，`pageStarts` 缺失 | `page=0`，前端不显示页码 | 重新上传；或落盘原文件后重解析 |
| 无原始文件 | 只存文本 | 无法做页面高亮、图片裁剪 | 09 需要先补原文件落盘 |
| 固定字符切分 | 不感知语义/句子边界 | 可能切断表格/公式 | 元素级切分（09） |

## 八、验证与回归

当前可用的验证手段：

1. **失败归因实验** `eval/scripts/attribute_failures.py`：
   14 篇论文 / 2181 chunk / 188 条查询，正文 Recall@5 72.9%、可答率 85.0%；
   图表查询 Recall@5 58.3%、可答率 70.8%。失败中排序 19 条、覆盖 16 条（figure 12 / table 4）。
2. **召回评测** `eval/README.md` 里的五臂对比：**改了 chunk 边界就必须重跑**，
   否则新旧指标不可比。
3. **重建脚本**：任何解析/切分改动后，用 `reindex_kb.py --prune-legacy` 重建并核对
   `chunks / sections` 数量。

改动本链路的验收底线：

- 正文查询 Recall@5 不低于当前 72.9%（同语料同查询集）；
- `page` 映射抽样正确（chunk 的 `charStart` 落在对应页区间内）；
- 删除文件后 Milvus / `file_sections` / `fileanagements` 均无残留。
