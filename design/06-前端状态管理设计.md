# 06 · 前端状态管理设计（Vue / Pinia / store）

> 本文记录前端状态层的一次梳理与重构：明确 Vue、Pinia、`src/store` 三者的职责边界，
> 说明状态为什么必须集中管理、数据到底存在内存还是磁盘，以及把单一 `projectStore`
> 拆成 `user` / `chat` / `ui` 三个 store、修正 `sessionId` 语义的设计决策。
> 涉及范围仅限 `project-user/src`，不触碰后端与 RAG 链路。

---

## 一、问题起点：组件树与数据的错位

当前组件树（`AppShell.vue` 是唯一布局根）：

```
main.ts
 └─ App.vue
     └─ AppShell.vue
         ├─ ChatHistory.vue   左侧边栏：会话列表、登录/退出、知识库入口
         ├─ ChatWindow.vue    消息展示区
         ├─ ChatInput.vue     底部输入框
         ├─ Knowledge.vue     知识库抽屉
         └─ UserLogin.vue     登录弹窗
```

五个组件**全部平级**，不存在深层嵌套。而数据的使用分布是跨组件的：

| 数据 | 写入方 | 读取方 | 冲突类型 |
|---|---|---|---|
| `userInfo` / `token` | `UserLogin.vue` 登录成功、`request.ts` 401 时 | `ChatHistory.vue` 渲染用户区、`ChatInput.vue` 发送前校验、`request.ts` 挂鉴权头 | 兄弟组件 + 非组件模块 |
| `sessionId` | `request.ts` 收到 SSE `sessionId` 帧、`ChatHistory.vue` 切换会话 | `ChatInput.vue` 请求体、`ChatHistory.vue` 高亮当前项 | 非组件模块 → 组件 |
| `messageList` | `ChatInput.vue` push、`request.ts` 流式追加 | `ChatWindow.vue` 渲染、`ChatHistory.vue` 监听条数刷新列表 | 兄弟组件双向 |
| `showLoginPopup` | 顶部按钮、发送拦截、401 自动弹窗 | `UserLogin.vue` 弹窗显隐 | 三个触发源 |

这四类冲突，Vue 的组件内机制（`ref` / `props` / `emit`）**一个都解决不了**——尤其第 2、3 行，
写方是 `request.ts`，它根本不是组件。

## 二、Vue 原生方案的边界

| 方案 | 作用域 | 本项目的失效场景 |
|---|---|---|
| `ref` / `reactive` | 单个组件实例，随组件销毁 | 兄弟组件读不到；`request.ts` 读不到 |
| `props` | 父 → 子单向 | 需要把状态提升到 `AppShell`，五处传参 + emit 回传 |
| `emit` | 子 → 父 | 同上，且无法向"组件树外"通知 |
| `provide` / `inject` | 祖先 → 后代 | `request.ts` 不在组件树内，`inject()` 无上下文；注入是静态的，跨模块取值不成立 |
| 事件总线 / `mitt` | 全局 | 只能传事件，不保存状态；组件挂载顺序不同会漏事件 |

结论：**只要存在"非组件模块（网络层、工具函数）需要读写应用级数据"的需求，组件内机制就必然失效**，
必须引入一个位于组件树之外的容器。这正是 Pinia 的位置。

## 三、Pinia 的定位

**一句话**：Pinia 是 Vue 官方推荐的状态管理库，提供"活在组件树之外、但被 Vue 响应式系统追踪"的全局数据容器。

拆解为三个属性：

1. **在组件树之外** —— store 的生命周期与任何组件无关，组件卸载后数据仍在；
   且可被 `request.ts` 这类纯 TS 模块直接 `import` 后使用。
2. **被响应式系统追踪** —— `state` 由 `reactive()` 包装，任意位置修改都会触发依赖它的组件重渲染。
   这是它与"普通全局对象"的本质区别。
3. **官方推荐** —— Vuex 的继任者，Vue 3 生态标准方案。

内部机制只有三步，并不神秘：

```
defineStore(id, options)
  → 生成一个"取 store 的函数"（useXxxStore）
  → 首次调用：用 reactive() 包装 state，创建实例，存入 pinia 实例的 Map
  → 之后调用：从 Map 直接返回同一对象（单例）
```

与"手搓 `export const global = reactive({...})`"的差别：

| 能力 | 手搓全局对象 | Pinia |
|---|---|---|
| 响应式 | 需自己包 `reactive` | 内置 |
| 单例管理 | 依赖模块缓存 | pinia 实例级 Map，多 app 隔离 |
| 结构约束 | 无，易演变为意大利面 | `state` / `getters` / `actions` 三区分离 |
| 派生状态 | 手写 `computed` | `getters` 天然是 computed，带缓存 |
| 调试 | `console.log` | Vue Devtools 状态快照、时间旅行 |
| 类型推导 | 弱 | 全链路推导，`vue-tsc` 直接受益 |
| 插件 | 无 | 持久化、日志等生态插件 |

## 四、store 不是"数据仓库"：三层存储的区分

`src/store/*.ts` 是**代码（图纸）**，不是数据。真正存放数据的有三层：

| 层 | 位置 | 内容 | 刷新页面 | 关闭浏览器 | 跨标签页 |
|---|---|---|---|---|---|
| 源码 | 磁盘 | `defineStore` 定义 | 不变 | 不变 | 不变 |
| **store 实例** | **内存（JS 堆）** | `userInfo`、`messageList`、弹窗开关 | **重置为初始值** | 消失 | **各标签页独立** |
| `localStorage` | 浏览器磁盘 | `'userInfo'`、`'sessionId'` 两个 key | 保留 | 保留 | 共享 |

运行时序：

```
① 加载 bundle
② app.use(pinia)        → pinia 实例创建（此时一个 store 都还没有）
③ useUserStore()        → 首次调用才创建 user store（reactive 对象进内存）
   initFromStorage()    → 从 localStorage 搬回 userInfo
④ 各组件调用 useXxxStore() → 命中 Map，拿到同一个对象
⑤ userLogin()           → 改内存 + 写 localStorage
⑥ messageList.push()    → 只改内存
⑦ F5 刷新               → userInfo 复活；messageList 归零
```

**只有 action 里显式 `setItem` 的数据能穿过刷新。** 当前项目中：

- `userInfo` 持久化（`store/user.ts:24`、回读在 `store/user.ts:33-42`）
- `sessionId` 持久化（`store/chat.ts:27-31`），但**没有回读逻辑**——见第十节遗留项
- `messageList`、弹窗开关不持久化（属当前会话/瞬时 UI 状态）

### 内存与"缓存"的用词边界

项目内存在四种易混的"缓存"，需明确区分：

| 名称 | 位置 | 存什么 | 管理者 |
|---|---|---|---|
| store state | 内存 | 当前会话、登录态、弹窗 | Pinia |
| localStorage | 浏览器磁盘 | 登录态（跨刷新） | `user` / `chat` store 的 action |
| HTTP 缓存 | 浏览器 | 静态资源 | 浏览器，按响应头 |
| Redis | 后端内存 | 对话历史（`HISTORY_TTL`） | `py-serve/app/chat` |

规律：**内存是活的（驱动界面），磁盘是死的（撑过刷新）；活的操作视图，死的负责持久化。**

## 五、职责划分：为什么拆成三个 store

重构前是单个 `projectStore`（`id: 'app'`），5 个互不相关的字段挤在一起，任何组件 import 就拿走全部。

拆分后：

```
src/store/
├─ index.ts    barrel：export * from './user' | './chat' | './ui'
├─ user.ts     useUserStore  → userInfo（+ localStorage）
├─ chat.ts     useChatStore  → sessionId + messageList
└─ ui.ts       useUiStore    → showLoginPopup / knowledgePopup
```

| store | 状态 | 生命周期 | 主要读写方 |
|---|---|---|---|
| `user` | `userInfo` | 登录 → 退出；跨刷新恢复 | `UserLogin` 写，`ChatHistory` / `ChatInput` / `request.ts` 读 |
| `chat` | `sessionId`、`messageList` | 新建/切换会话 | `ChatInput` 写消息、`ChatWindow` 读消息、`request.ts` 写 sessionId |
| `ui` | 两个弹窗开关 | 瞬时 | 三处触发，`UserLogin` / `Knowledge` 消费 |

**划分原则（三条，按优先级）：**

1. **谁能改** —— 写入方是否同一类。登录态只由登录/登出/启动恢复改写，归 `user`；
   会话只由发消息/切会话改写，归 `chat`。
2. **谁要读** —— 读取方决定耦合面。把弹窗开关单独放，避免 `Knowledge.vue` 为了读一个布尔
   而拿到整个用户和消息列表。
3. **活多久** —— 生命周期不同就不该同居。`userInfo` 跨刷新，`sessionId` 跨组件但不过刷新，
   弹窗开关只活几秒。

**依赖方向保持单向**：`user.ts` → `chat.ts`（登出时调 `resetSession`），`chat.ts` 不反向依赖；
`index.ts` 仅做出口，不含逻辑，避免 barrel 形成循环引用。

## 六、关键设计决策

### 1. `sessionId` 内部用 `null`，边界序列化为 `"null"`

**后端契约**（不可改）：

```88:88:py-serve/app/chat/service.py
is_new_session = session_id == "null"
```

`schemas.py` 中 `sessionId: str`，传 `null` 会被 422 拦截。因此 `"null"` 必须保留，
但只允许出现在**请求边界**：

```17:24:project-user/src/store/chat.ts
  state: () => ({
    sessionId: null as string | null,
    messageList: [] as MessageListType[],
  }),
  getters: {
    // 请求体里用的 sessionId，屏蔽后端 "null" 字符串的约定
    sessionIdForApi: (state): string => state.sessionId ?? NEW_SESSION_ID,
  },
```

调用方写 `chat.sessionIdForApi`（`ChatInput.vue:287`），其余判断"是否新会话"直接用 `if (chat.sessionId)`。
修正前 `'null'` 是 truthy，这类判断全部失效。

配套修正：

| 项 | 修正前 | 修正后 | 理由 |
|---|---|---|---|
| 命名 | `getSessionId()` | `setSessionId()` | 名为 get 实为写，误导 |
| 新会话的磁盘值 | 存字符串 `'null'` | `removeItem` | 磁盘不应出现假 id |
| 写入路径 | 3 个 action 各写一遍 | 收敛到 `setSessionId` 唯一入口 | 避免格式漂移 |
| 反序列化 | 无 try/catch | 加保护并清理脏数据 | 坏数据会导致整页白屏 |

### 2. UI 状态独立，并提供具名 action

```ts
openLoginPopup() / closeLoginPopup() / openKnowledgePopup()
```

原写法是 `getStore().showLoginPopup = true`（`request.ts` 隔空改字段），现改为
`useUiStore().openLoginPopup()`，调用点自解释，且把"哪些字段可以被外部改"收敛到 action 层。
`v-model` 仍直接绑定 `ui.showLoginPopup`（Vue 需要可写属性），两条路径并存是刻意的。

### 3. 惰性获取 store，禁止模块顶层调用

`request.ts` 在 `main.ts` 的 `app.use(pinia)` **之前**就被 import 链加载（ESM 静态提升），
顶层调用 `useXxxStore()` 会抛 `getActivePinia() was called but there was no active Pinia`。
因此统一在函数/拦截器执行时再取：

```9:11:project-user/src/api/request.ts
// 注意：不要在模块顶层调用 useXxxStore()，
// 本模块会在 main.ts 完成 app.use(pinia) 之前被加载，顶层调用会报 "active pinia" 错误。
// 统一在函数 / 拦截器真正执行时再取（此时 pinia 已安装）。
```

替代方案是"显式传入 pinia 实例"（`useXxxStore(pinia)`，pinia 由独立模块导出），
可彻底摆脱初始化顺序依赖，但需改动全部调用点，当前不必要。

### 4. 依赖链：登出同时清会话

`userLogout()` 内调用 `useChatStore().resetSession()`（`store/user.ts:27-31`），
保证退出登录后不会残留上一个用户的消息。为避免反向依赖，`chat.ts` 不感知 `user`。

### 5. 导入路径统一使用 `@/` 别名

`user.ts` 对 `chat.ts` 的引用写作 `@/store/chat` 而非 `./chat`。
原因：IDE 的 TS 语言服务对新建文件的相对路径解析曾报 TS2307（`vue-tsc` 正常），
走 `paths` 映射后稳定，且与全项目风格一致。

## 七、三个与 store 相关的框架层陷阱

| 陷阱 | 现象 | 规避方式 |
|---|---|---|
| 顶层调用 `useXxxStore()` | `no active pinia`，白屏 | 惰性获取（第六节 3） |
| 解构 state | 数据变了界面不动 | `const user = useUserStore()` 后 `user.xxx`；必须解构时用 `storeToRefs` |
| 流式更新传副本 | 内容累积但界面不刷新 | 必须传数组内的响应式对象引用（`ChatInput.vue:276-277`） |

第三条是本项目最特殊的一处：`SendMessageApi` 的第二个参数 `aiMessageObj`
**必须是 `chat.messageList` 里的那个对象**，因为流式增量是直接对 `content` / `readFileData`
赋值，只有持有原引用才能触发 Vue 的依赖更新。

## 八、一次完整链路的层次标注（发消息）

```
① ChatInput 输入并点击发送                         Vue 组件层
② if (!user.isLogin) → ui.openLoginPopup()        读 store（user / ui）
③ chat.messageList.push(用户消息, AI 占位)          写 store（chat）
④ 取 const aiMessageObj = messageList[末位]        持有响应式引用
⑤ SendMessageApi(..., aiMessageObj)               进入网络层（组件之外）
⑥ 拦截器挂 Authorization: Bearer userStore.token   网络层读 store（user）
⑦ SSE 帧 type:'answer' → content += 片段           网络层写 store（chat）
⑧ Vue 检测变化 → ChatWindow 重渲染                 视图层自动跟随
⑨ 帧 type:'sessionId' → chat.setSessionId()       网络层写 store（chat + 磁盘）
⑩ ChatHistory 的 is-active 自动变化                另一个组件被动响应
```

⑦→⑧ 是核心：网络层改字段，视图层自动更新，两者之间无任何直接调用、事件或 props。

## 九、边界判定：什么情况不该用 store

| 场景 | 用 store | 原因 |
|---|---|---|
| 仅父子传递 | ❌ | `props` 足够，避免过度设计 |
| 只在本组件使用的输入内容 / 加载态 | ❌ | 生命周期与组件一致 |
| 弹窗开关，且只有一个组件能打开 | ❌ | 组件内 `ref` 即可 |
| 弹窗开关，多处可触发 | ✅ | `showLoginPopup` 即此类 |
| 需要给网络层 / 工具函数读写的 | ✅ | 组件内机制覆盖不到 |
| 跨路由 / 跨刷新需保留 | ✅ | 只有 store + localStorage 能做 |
| 多处共享同一份实体（列表 ↔ 详情） | ✅ | 避免重复请求与状态不一致 |

对照现状：`userMessage`、`sending`、`isActive`（`ChatInput.vue:125-129`）保留为组件内 `ref` 是正确的，
它们只服务单个组件；`user` / `chat` / `ui` 三个 store 的字段则全部满足上表的 ✅ 条件。

## 十、已知遗留与后续可选

| 项 | 说明 | 建议 |
|---|---|---|
| `sessionId` 只写不读 | `setSessionId` 会写 localStorage，但启动时无回读逻辑 | 要么补 `initSessionFromStorage()` 并同时持久化 `messageList`，要么删掉该写入；当前保留写、不回读，避免"刷新后空白页却续写老会话" |
| `messageList` 全量驻留内存 | 长对话不释放，靠切会话整体替换数组回收 | 会话量级增大后考虑分页或虚拟滚动 |
| 多标签页不同步 | localStorage 共享，但内存各自独立 | 如需同步，监听 `window.storage` 事件并回写 store |
| 持久化样板代码 | 每个持久化字段手写 `setItem` | 可引入 `pinia-plugin-persistedstate`，但需处理"内存 `null` ↔ 磁盘 `'null'`"这类序列化差异 |
| 无 devtools 命名规范 | store id 已区分 `user` / `chat` / `ui` | 保持，勿再合并回单一 `app` |
