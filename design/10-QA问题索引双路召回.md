# 10 · QA 问题索引双路召回

> 本文记录「为每个 chunk 预生成用户可能问的问题，查询时做问题对问题匹配」
> 从离线实验到生产落地的设计与实现。
> 相关评测：[09 图表提取设计](09-图像与图表提取设计.md) 的失败归因，
> 以及 `py-serve/eval/README.md` 的 QA 对照实验。
>
> 代码：`app/file_management/qa_index.py`、`service.py`、`scripts/reindex_kb.py`。

## 一、结论先行

在 1563 chunk / 8644 个索引问题 / 3046 条查询的离线实验里：

| 实验臂 | Recall@5 | 相对 chunk 向量 |
|---|---|---|
| chunk 向量 | 66.5% | — |
| QA 单路（RRF） | 73.2% | +6.7pt |
| **chunk + QA（RRF 0.5/0.5）** | **78.8%** | **+12.3pt** |
| 生产关键词 hybrid | 65.1% | -1.4pt |
| 关键词 + QA | 78.5% | +12.0pt |

结论：

1. 「问题对问题」有效，单路 +6.7pt，融合 +12.3pt；
2. 融合已经覆盖了关键词路的收益，关键词路没有继续保留的必要；
3. 聚合方式用 `max` 或 `RRF`，不要用 `mean`（平均会把唯一匹配的问题稀释掉）。

因此生产采用：**chunk 向量 + QA 问题路双路 RRF（0.5/0.5）**，
QA 索引不存在或为空时降级回「chunk + 关键词」。

## 二、目标与非目标

**目标：**

1. 上传知识库文件后，为每个 chunk 自动生成 5 个用户可能问的问题；
2. 查询时并行检索 chunk 向量与问题向量，映射回 chunk 后做 RRF；
3. 不阻塞上传响应，索引构建状态可追踪；
4. 删除文件时同步清理问题向量；
5. 无 QA 索引的存量用户自动降级，不报错。

**非目标：**

- 不做 query 改写/HyDE（当前只有 QA 索引这一路）；
- 不在本次接入 reranker；
- 不为图表/表格单独生成问题（等 09 的元素索引落地后再扩展）。

## 三、数据模型

### 3.1 Milvus：`_<userId>_qa_v1`

```text
id          Int64 主键（手动生成）
docId       VARCHAR(100)
docTitle    VARCHAR(500)
chunkKey    VARCHAR(200)   → 映射回 chunk 集合
questionId  VARCHAR(250)   → chunkKey#qN
question    VARCHAR(1000)
qVector     FloatVector(1024)
```

索引：`IVF_FLAT + COSINE, nlist=128`，检索 `nprobe=10`。

**为什么单独一个集合？**

- 问题向量是 chunk 向量的 5 倍，混在一起会让 chunk 检索的统计/过滤变复杂；
- 问题行只需要 `chunkKey` 和问题文本，正文仍以 chunk 集合为准，避免同一段文本重复 5 份；
- schema 变更只影响 QA 集合，不用再动 chunk 集合（v3）。

### 3.2 Mongo：`fileanagements`

新增字段：

```text
qaStatus     pending | building | ready | failed    （对话框文件为 None）
qaBuiltAt    datetime
qaQuestions  int
qaError      string（失败原因，截断 500 字）
```

`qaStatus` 只用于运维可见性，检索侧不依赖它：即使状态还是 `building`，
已经写入的问题向量也可以被检索，chunk 路始终兜底。

## 四、入库流程

```
POST /file_management/knowledge
   │
   ├─ 解析 + 切分 + chunk 向量入库（同步，与现状一致）
   ├─ 父章节 file_sections 入库
   ├─ Mongo 写入 qaStatus=pending
   └─ asyncio.create_task(_build_qa_index)
          │
          ├─ qaStatus=building
          ├─ 每个 chunk 一次 LLM：生成 5 个问题
          ├─ 所有问题批量 embedding（Qwen，10 条/批）
          ├─ 写入 _<userId>_qa_v1
          └─ qaStatus=ready / failed
```

### 4.1 为什么异步

一个 100 chunk 的文档需要 100 次 LLM 调用 + 500 次问题 embedding。
同步做会让上传从几秒变成几分钟，前端 loading 无法接受。

上传响应返回时，chunk 已经可检索；QA 索引在后台补齐，期间检索自动走纯 chunk 路。

### 4.2 问题生成

- 模型：`Config.DEEPSEEK_MODEL`（flash），`temperature=0.7`；
- 每个 chunk 1 次调用，要求输出 5 个问题；
- 约束：必须能仅凭该 chunk 回答、口语化、不照抄原文、覆盖不同侧面；
- 失败重试 3 次；单 chunk 最终失败只跳过该 chunk，不阻断整篇；
- 单 chunk 的问题去重保序，最多 6 个。

### 4.3 并发与限流

- LLM 并发 4（`LLM_CONCURRENCY`），避免触发 DeepSeek 限流；
- embedding 复用现有 `embedding_client`（批量 10、并发 4、失败重试）；
- 日志每 20 个 chunk 打印一次进度。

### 4.4 失败与删除

- 构建失败：`qaStatus=failed`、`qaError` 记录原因，chunk 检索不受影响；
- 构建期间文件被删除：任务完成后检查文件是否还存在，不存在则删除已写入的问题向量；
- 删除文件：先删 chunk 向量 → 再删 QA 向量 → 删父章节 → 删 Mongo 文件记录；
  QA 删除失败只记日志，不阻断文件删除（检索侧取不到 chunk 正文会自动跳过）。

## 五、检索流程

```
query
  │
  ├─ embed_query（一次）
  │
  ├─ chunk 集合 search top10 ─────────────┐
  │                                      ├─ RRF（0.5 / 0.5）→ top5
  └─ QA 集合 search top30 问题            │
        → 按 chunkKey 去重取 top10        │
        → 按 chunkKey 回表 chunk 集合 ────┘
  │
  └─ QA 为空/集合不存在 → chunk + 关键词 RRF（0.7/0.3）兜底
```

实现位置：`service.hybrid_search`。

要点：

- **只 embed 一次**：chunk 路与 QA 路共用 query 向量；
- QA 命中是「问题」粒度，必须按 `chunkKey` 去重，再回表取正文与溯源字段；
- 融合 key 优先用 `chunkKey`，避免同一段文本因截断差异被当成两个条目；
- `hitVector / hitQA / hitKeyword` 三个标记透传到 citation 的 `matchedBy`，
  前端可区分是语义命中还是问题索引命中；
- QA 路异常时降级到关键词路，不把整次检索打挂。

### 5.1 为什么不再融合关键词

实验里 D（chunk + 关键词）比 A 低 1.4pt，E（D + QA）与 C（A + QA）持平。
关键词路的收益已经被 QA 路覆盖，继续三路融合只会增加一次 LLM 提词调用和噪声。

保留 `keyword_search` 仅用于降级与调试接口。

### 5.2 父子上下文

QA 命中映射回 chunk 后，仍走原有的父章节聚合：

- 同一父章节的多个命中合并；
- 窗口 = 子块 ± 600 字，单片段上限 2400 字；
- 父章节按一级章节存储（见 08），避免极短小节把窗口压成十几个字。

## 七、成本与容量

| 项 | 估算 |
|---|---|
| LLM | 1 次/ chunk（生成 5 个问题） |
| embedding | 5 次/ chunk（问题向量） |
| 向量存储 | chunk 向量的 5 倍 |
| 上传延迟 | 不增加（后台任务） |
| 查询延迟 | 多一次问题向量检索（毫秒级） + 一次 chunk 批量回表 |
| 重建成本 | 419 chunk 的知识库约 2095 个问题，约 5~8 分钟 |

## 八、运维与迁移

### 8.1 重建

```bash
# 重建 chunk + 父章节 + QA（完整）
python scripts/reindex_kb.py

# 只重建 chunk 与父章节，保留现有 QA（仅当 chunk 边界未变）
python scripts/reindex_kb.py --skip-qa

# 单个用户
python scripts/reindex_kb.py --user-id <id>
```

### 8.2 重要约束

**只要 chunk 边界变了，就必须重建 QA 索引。**
QA 行通过 `chunkKey = docId#chunkIndex` 关联 chunk；切分参数、解析器、
章节识别任一改动都可能导致 chunkIndex 位移，旧的 QA 会指到错误的 chunk 上。
`--skip-qa` 只适用于「不动切分、只修父子/向量」的场景。

### 8.3 重启

后台任务是进程内的 `asyncio.create_task`，服务重启会丢失正在构建的任务：

- 已写入的部分问题向量仍可用；
- `qaStatus` 可能停留在 `building`；
- 重新上传或跑一次 `reindex_kb.py` 即可恢复。

当前项目是单进程，暂不引入任务队列；如果要上多实例，应换成 Celery/RQ 或独立 worker。

## 九、评测与验收

离线评测（`run_qa_rerank_eval.py`，3046 查询）：

- chunk 66.5% → QA 单路 73.2% → 双路 78.8%（Recall@5）；
- MRR 0.515 → 0.563 → 0.598；
- DocRecall@5 96.1% → 97.5% → 98.0%。

上线验收：

1. 新上传文档 `qaStatus=ready` 且 `qaQuestions ≈ chunks × 5`；
2. `hybrid_search` 返回 `fromQA > 0`，top5 中至少一部分 `hitQA=true`；
3. 删除文件后 QA 集合无该 `docId` 行；
4. 存量无 QA 的用户仍能正常检索（降级路径）；
5. 同一 query 的引用 `matchedBy` 能体现 `qa` 命中。

注意：离线评测语料是改造前的 1563 chunk，当前 v3 切分的绝对值需要重新生成
QA 索引后再测；策略方向（QA 有效、mean 无效、关键词无增量）可复用。

## 十、风险

| 风险 | 表现 | 对策 |
|---|---|---|
| LLM 限流/超时 | 部分 chunk 没有生成问题 | 并发 4、重试 3 次、状态置 failed、可重跑 |
| 问题质量差 | 问题与 chunk 无关 | prompt 约束 + 评估抽样；后续可人工抽检 |
| 索引与 chunk 错位 | 引用指到错误片段 | 切分变更必须重建 QA；`qaStatus` 与 `qaQuestions` 可核对 |
| 存储膨胀 | 问题向量 5 倍 | 按用户配额；问题数可降到 3~4 做取舍 |
| 后台任务丢失 | 重启后状态停在 building | 提供重跑脚本；后续引入队列 |
| 部分索引可用 | 检索结果不稳定 | chunk 路始终并行，QA 只是加分项 |
| 降级逻辑复杂 | 两套融合路径 | 只用 `hitQA` 区分；QA 为空即走旧逻辑 |
