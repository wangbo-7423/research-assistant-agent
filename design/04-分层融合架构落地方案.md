# 04 · 分层融合架构落地方案

> 本文把 00 总览中的分层架构落成 nest-serve 的具体改动点。
> 前提：已读过 [01](01-经典多路召回.md)（经典多路保持开启）、
> [02](02-维度拆分召回.md)（拆分降级为结构化层）、
> [03](03-Wiki编译期综合.md)（wiki 编译管线与门禁）。

---

## 一、目标架构（分意图、分层次）

```
用户问题
   │
   ▼
IntentRouter（现有，不动）
   │
   ├─ clarify ──► 现有链路，不动
   │
   ├─ fact ─────► 现有链路：hybridSearch + preciseSearch（raw chunk，逐字引用）
   │              ※ wiki 层不参与：事实类问题必须逐字溯源，wiki 是改写文本
   │
   └─ perspective ──► 【wiki 层】单路向量检索 wiki 集合，topK=3~12
                        │ 命中（最高 score ≥ 阈值 或 结果数 ≥ 1）
                        ▼
                     直接生成综述答案（可选：用拆分维度组织输出结构）
                        │
                        │ miss（集合不存在 / 0 命中 / 分数过低）
                        ▼
                     【raw 兜底】hybridSearch top12（现有组件，零改动）
```

关键决策及理由：

| 决策 | 理由（实测依据） |
|---|---|
| perspective 走 wiki **单路**，不做关键词融合 | wiki 是编译产物，文本规整，向量单路 W12=0.400 已验证；多路融合在规整语料上增量≈0（01 的结论同样适用） |
| wiki 优先、raw 兜底，而**不是**两层合并 | 合并需要跨层 rerank，实测 rerank 是多样性杀手（02 陷阱 3）；分层串行没有这个问题 |
| fact 路径完全不走 wiki | 逐字引用能力只有 raw 有（03 风险 3） |
| 拆分维度只做输出组织，不做召回 | B++ v3 实测追不平免费方案（02），但维度结构对综述答案的可读性是真实资产 |

## 二、改动点清单（按文件）

### 1. `fileanagement.service.ts` —— 入库侧：上传后异步编译 wiki

- `handleUpload`（:176）流程末尾，文档 chunk 入库成功后，**异步**触发该文档的 wiki 编译
  （不阻塞上传响应；编译实测 32~215s/篇）；
- 编译逻辑：把 `eval/scripts/compile-wiki.ts` 服务化——抽出 `WikiCompilerService`，
  复用其 map-reduce 管线（25 chunk/段、并发 4、术语保留 prompt、reduce ≤2500 字）；
- 存储：写入独立 Milvus 集合 `_wiki_<userId>`（与 raw 集合平行），
  chunk 级别沿用现有 schema，`docTitle` 前缀 `[wiki]` 以便溯源与前端区分；
- Mongo `fileanagement` 文档增加字段：`wikiStatus: 'pending'|'compiling'|'ready'|'failed'`、
  `wikiCompiledAt`、（可选）`wikiLint` 报告引用；
- 重编译入口：文档删除时同步删除其 wiki chunks；提供手动重编译接口（调 lint 后使用）。

### 2. `chat.service.ts` —— 查询侧：perspective 链路改 wiki-first

`handlePerspective`（:875）当前流程是 `splitDimensions` → 逐维 `retrieveDimension`。
改为：

```
handlePerspective(userQuestion, ...):
    0. flag RAG_PERSPECTIVE_LAYER=raw 时走原链路（灰度默认），=wiki 时进入下方分层流程
    1. wikiHits = fileanagement.wikiSearch(userQuestion, userId, topK=12)
       （专用方法：单路向量打 _wiki_<userId> 集合，返回 { exists, results }；
        集合不存在返回 exists=false 而非抛异常——「未编译」是预期内状态，
        与基础设施故障区分记因，避免降级率监控被污染）
    2. if wikiHits.exists 且 top1.score ≥ 阈值（RAG_WIKI_HIT_THRESHOLD，初值 0.3，灰度期扫参）:
           sources = wikiHits；trace 记 kb_layer='wiki'
       else:
           sources = fileanagement.hybridSearch(userQuestion, raw集合, topK=12)
           trace 记 kb_layer='raw_fallback'、kb_fallback_reason（not_compiled/no_hits/below_threshold/error）
    3. 生成阶段二选一：
       a. 简单版（推荐先上）：单轮生成综述答案，sources 直接喂入；
       b. 增值版（后做）：仍调 splitDimensions，但只用维度名做答案小节结构，
          不再逐维检索——保留结构资产，去掉 41s 成本。
```

- **IntentRouter 不动**：意图分类与召回层正交；
- **Confidence-Checker 适配**：置信度评估的 docTitle 来源要识别 `[wiki]` 前缀，
  归因级别从"chunk"放宽到"文档"（与评测口径一致，见 03 口径说明）；
- **trace 增加字段**：`kb_layer: 'wiki' | 'raw_fallback'`，
  以及 wiki 命中数/top1 分数——这是上线后调阈值和观察降级率的核心数据。

### 3. 运维配置 —— feature flag 与回退

- 环境变量 `RAG_PERSPECTIVE_LAYER=wiki|raw`（默认灰度期 `raw`，按用户灰度切 `wiki`）；
- 任何时刻把 flag 打回 `raw`，链路立即退化为当前生产行为（加一道保险：
  wiki 检索抛异常时 catch 住并自动落 raw 兜底，与现有维度收敛兜底同款思路）。

## 三、上线门禁（不过不上线）

| 门禁 | 标准 | 依据 |
|---|---|---|
| 回归评测 | 同评测集 wiki 路方面覆盖 ≥ 0.269（raw 经典多路线），实测已达 0.400 | 03 三节 |
| 编译 lint | 术语保留率达标 + 主题清单全覆盖 + grounding 抽查通过，见 03 五节 | 防 d03 式丢 9 个小节 |
| 降级率监控 | 上线首周 `raw_fallback` 比例 < 30%（过高说明 wiki 覆盖或阈值有问题） | trace 新字段 |
| 延迟 | perspective 链路 P95 不应比现状（拆分版 ~41s）更慢——wiki 单路预期 ~3s，反而是大幅改善 | 02 成本数据 |

---

## 四、灰度与迭代路线

1. **第一期（最小闭环）**：WikiCompilerService 服务化 + wiki-first 简单版生成 + flag 灰度。
   此时拆分链路整体下线（或 flag 保留），perspective 从 ~41s 降到 ~3s，覆盖 0.269→0.400；
2. **第二期**：编译 lint 门禁自动化 + 按主题拆多篇（解决 d03 压缩损耗，03 六节）；
3. **第三期**：拆分维度回归为答案结构层（生成版 b）+ 增量编译收敛时效性。

---

## 五、风险与回退

| 风险 | 触发信号 | 应对 |
|---|---|---|
| wiki 未编译导致召回空 | `raw_fallback` 比例高 | 正常现象（兜底生效）；监控并在编译失败率 >5% 时告警 |
| 编译质量差 | lint 门禁不过 / 用户反馈"答案太泛" | flag 打回 `raw`，链路秒级还原 |
| 新文档时效 | 上传后短时间内问新内容答不上 | 上传响应中提示"知识页编译中"；必要时对刚上传文档强制 raw |
| 多语言/新语料类型 | 换 embedding 或扩库 | 重跑 `run-perspective-ablation.ts`，重新校准阈值与配额 |

---

## 六、一句话总结

三层各司其职：**wiki 层负责覆盖（0.400），raw 层负责兜底与逐字引用，
经典多路作为便宜的地基常开，维度拆分退居输出结构层。**
改动集中在 fileanagement 加一个异步编译钩子、handlePerspective 换一个检索目标，
其余组件零改动，且有 flag 级一键回退。

## 七、第一期落地记录（2026-09-07 已实现）

| 改动点 | 文件 | 说明 |
|---|---|---|
| wiki 集合单路检索 | `fileanagement.service.ts` · `wikiSearch` | 返回 `{ exists, results }`：集合未编译是预期内降级信号（exists=false），基础设施异常才抛错——上层据此区分记因，降级率监控不被故障噪音污染 |
| 编译器服务化 | `wiki-compiler.service.ts` | map-reduce 管线移植自 `eval/scripts/compile-wiki.ts`（25 chunk/段、并发 4、术语保留 prompt、reduce ≤2500 字 + 空输出重试），全链路异常收敛为 `wikiStatus=failed` |
| 上传钩子 | `fileanagement.controller.ts` · `uploadKnowledge` | 上传成功后 fire-and-forget 触发编译，不阻塞响应；`RAG_WIKI_COMPILE=false` 可整体关闭 |
| 重编译入口 | `POST fileanagement/wiki/recompile/:id` | 校验文件归属后触发；编译状态经 `kbfilelist` 的 `wikiStatus`（none/pending/compiling/ready/failed）可见 |
| wiki 分片生命周期 | `deleteWikiChunks` | 文档删除时同步清理 `_wiki_<userId>` 分片；重编译前先清旧分片防重复；编译完成入库前复核文档仍存在（upload→delete 竞态防孤儿分片） |
| perspective 分层 | `chat.service.ts` · `handlePerspectiveWiki` | wiki-first + raw 兜底（串行不合并），单轮流式综述（简单版 a）；`[wiki]` 前缀在展示与置信度归因处统一还原为源文档名；raw 兜底结果不传 RRF 分给置信度检查（量纲不同，走缺省值与原链路口径一致） |
| trace 字段 | `kb_layer` / `kb_fallback_reason` / `wiki_hits` / `wiki_top_score` / `wiki_top_k` / `wiki_hit_threshold` | 上线后调阈值与观察降级率的核心数据 |

新增环境变量（见 `.env.example`）：`RAG_PERSPECTIVE_LAYER`（默认 raw）、`RAG_WIKI_TOPK`（默认 12）、
`RAG_WIKI_HIT_THRESHOLD`（默认 0.3）、`RAG_WIKI_COMPILE`（默认 true）、`WIKI_COMPILE_MODEL`（可选）。

灰度开关操作：`.env` 中 `RAG_PERSPECTIVE_LAYER=wiki` 切入分层链路，任何时刻改回 `raw`
即还原现网维度拆分行为，无需回滚代码。上线门禁（回归评测 ≥ 0.269、编译 lint、降级率 < 30%）
按第三节执行；0.400 为 n=8 实验值，门禁线下限取 0.269 更稳妥。
