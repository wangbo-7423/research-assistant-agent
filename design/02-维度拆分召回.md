# 02 · 维度拆分召回（查询侧）

> 定义：把**同一个问题**拆成多个"方面/视角"子查询，每个子查询独立检索，
> 再按维度配额合并。治的病是「单查询的语义覆盖不足」——一个问题天然有多个侧面，
> 单个向量只能偏向其中一个。
>
> 对应本项目 Perspective-Analyzer：`sub-agent.ts` 的 `splitDimensions` +
> `chat.service.ts` 的 `handlePerspective`（chat.service.ts:875）。

---

## 一、机制图：查询侧多路

```
                     用户问题
                        │
                        ▼
              ┌──────────────────┐
              │  splitDimensions │  LLM 拆解为 2~6 个维度
              │  （sub-agent.ts）│  每维 { name, query, weight }
              └──────────────────┘
                        │
        ┌───────┬───────┼───────┬───────┐
        ▼       ▼       ▼       ▼       ▼
      维度1   维度2   维度3   维度4   维度5     ← 同一通道 × 多个子查询
        │       │       │       │       │
        ▼       ▼       ▼       ▼       ▼
      各自检索 topK → 维内排序 → 按维度配额截取 → 合并
```

与经典多路（01）的本质区别：**多路在通道侧，拆分在查询侧**。
前者是"同一句话用几种方式理解"，后者是"把一个问题变成几个问题"。

---

## 二、实测历程：从负优化到追平（2026-09-07，8 题 × 33 方面）

| 版本 | 改动 | 方面覆盖 |
|---|---|---|
| B（生产实现） | 每维 top3 检索 + 全局 rerank | **0.156**（比单路 top3 的 0.125 只高一点，远低于单路 top12 的 0.269） |
| B+ | 修复拆解兜底 | 0.181 |
| B++ v1/v2 | 两阶段漏斗 + 维配额 | 0.237 / 0.244（中间迭代） |
| **B++ v3（最终）** | 锚定粗召回 + 材料喂入拆解 + 维配额 4 + 禁全局 rerank | **0.263** |
| 参考：单路 top12 | 什么都不做，只把 topK 拉大 | 0.269 |
| 参考：oracle 人工最优拆维 | 上限 | 0.725 |

**结论：烧掉 41s/题 和 1 次 LLM 调用，最好的维度拆分也只是追平"topK 调大"这个免费操作。**

## 三、四个实测陷阱（每个都是用实验数据换来的）

### 陷阱 1：拆解结果静默兜底

`sub-agent.ts:117`：LLM 拆解失败或格式不符时，静默回退到
「核心要点 / 局限与争议」两个通用维度。实测 **8 题中 7 题触发了兜底**——
意味着大部分时候系统根本没有在"拆分"，只是在用两个模板维度检索，却付出了拆分成本。

**教训：兜底路径必须计入指标监控，否则线上永远不知道拆分是否在工作。**

### 陷阱 2：抽象疑问句不可检索

LLM 自由生成的维度 query 形如「RAG 的优势体现在哪些方面？」——
这种疑问句向量与知识库中的陈述句 chunk 语义距离很远。
修复方式（B++ v3）：**把粗召回的材料片段喂给拆解 prompt，要求每个维度 query
必须引用材料原文术语**，让子查询"落地"。

### 陷阱 3：全局 rerank 再同质化

把各维度召回结果合并后做一次全局 rerank，直观上是"质量把关"，
实测却把并集覆盖 0.25 截成 0.00（p03 案例）：rerank 模型按与**原始问题**的
相关性重排，把"只在某个侧面相关"的 chunk 全部排掉——
维度拆分辛苦拉开的多样性被 rerank 一刀切回去了。

**教训：维度拆分之后禁止全局 rerank；维内 rerank 同样有害
（实测 p03/p04/p05 各因此丢失一个方面）。**

### 陷阱 4：维内截断位置

gold chunk 常落在维内 RRF 排序的第 4~6 位，配额 3 会系统性切掉它们，
配额 4 才稳定覆盖。这个"4"是当前语料和 embedding 的经验值，换库要重测。

## 四、B++ v3 最终形态（如果要继续用，就该这么用）

```
问题 ──► ① 粗召回 top20（单路向量，锚定语料）
           │
           ▼
        ② 落地拆解：粗召回片段 + 问题 → LLM
           （硬约束：每维 query 必须引用材料原文术语；失败兜底计入监控）
           │
           ▼
        ③ 每维独立深挖 top6
           │
           ▼
        ④ 维内 RRF 排序，顺序配额 4（维间按 weight 排序，维内禁 rerank）
           │
           ▼
        ⑤ 直接拼接，禁止全局 rerank
```

成本：**~41s/题**（1 次粗召回 + 1 次 LLM 拆解 + N 路检索），
对照单路 top12 约 3s/题。

---

## 五、方差警告

p02 同一配置三次运行覆盖率为 0.20 / 0.40 / 0.60。
维度拆分链路上有两个非确定性来源（LLM 拆解、多路并发检索时序），
**单次评测的 ±0.2 波动是常态**，任何 A/B 结论都必须多次运行取均值。

---

## 六、定位结论

| 问题 | 结论 |
|---|---|
| 要不要做召回主力？ | **不要。** 最好成绩（0.263）追平免费方案（0.269），成本 13 倍 |
| 是否毫无价值？ | 不是。它产出的**维度结构**本身是资产——答案按"原理/优势/局限/对比"组织，是综述类回答的骨架 |
| 推荐定位 | **降级为答案结构化增值层**：召回用 03 的 wiki 层或 raw top12，拆分只用于组织输出 |
| 未来优化方向 | 拆解结果缓存（同问题命中率应很高）；异步拆解不阻塞首 token |

---

## 七、一句话总结

维度拆分召回治的病是真的（oracle 上限 2.7×），
但"让 LLM 实时拆出可检索的子查询"这件事的实现难度吃掉了全部收益——
**同样的方面结构，让 LLM 在入库时慢慢做（03 Wiki），比查询时仓促做划算得多。**
